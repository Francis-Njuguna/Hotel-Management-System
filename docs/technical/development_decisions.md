# Architecture decision register — discovery baseline

Date: 2026-11-26. **Mandated** means specified in the owner's brief. **Proposed** means the principal recommends it but the owner has not approved it; no decision here is an implementation or a supervisor sign-off. Reference: [discovery report](../discovery_report.md).

| ID / status | Context and recommendation | Alternative, consequence and review trigger |
|---|---|---|
| ADR-001 · Mandated | One modular Django monolith, DRF, independently organized React/TypeScript client and PostgreSQL. One relational transaction can cover a stay, folio and turnover. | Microservices would require distributed consistency and extra operations without a demonstrated requirement. Change only by explicit owner approval. |
| ADR-002 · Proposed | Serve staff UI and `/api/v1/` under one HTTPS origin. Use Django's server-side sessions, CSRF protection including login, and backend action/record/field permissions. The browser never stores a bearer credential in local storage. | JWT would add refresh, rotation, revocation and browser-storage choices. Revisit if approved external/native clients require independent origins or delegated access. Trade-off: protect cookie writes with CSRF and operate a session store/expiry process. |
| ADR-003 · Proposed | Allocate physical rooms by hotel-local nights `[arrival, departure)`. A single room-claim calendar represents reservation lines and **blocking** maintenance windows. PostgreSQL rejects overlap for the same room on committed claims; the blocking predicate and range belong to that row. Atomic transitions and a consistent room-lock order protect cross-table readiness. | A read-then-insert availability check alone races. If `btree_gist` cannot be enabled, evaluate a per-room-per-night unique allocation shared by bookings and closure blocks; higher write volume. If the hotel sells hourly or unassigned category inventory, reassess model before schema work. |
| ADR-004 · Proposed | Distinguish bookable tonight/for a date range, actually occupied, awaiting inspection and unavailable due to maintenance. Store scheduled claims, actual stays and task/inspection history independently; derive room readiness. | One mutable room-status label cannot represent an occupied room booked for next week that also has an open nonblocking repair. Confirm check-in gates, override authority and emergency closure process. |
| ADR-005 · Mandated core; policy proposed | KES, fixed-precision amounts and no simulated receipts are required. Propose server-calculated decimal charge lines at agreed prices, actual receipts/payment records, unique posting sources, auditable corrections and separate metrics for charges and cash. Monetary API values are decimal strings. | A single editable 'paid' flag or mutable rate loses the reconciliation trail. Taxes, refund/credit authority, receipt evidence, posting time and financial reporting basis need finance approval. No gateway in baseline; M-Pesa is a future approved, verified integration only. |
| ADR-006 · Proposed | Synchronous application workflows coordinate domain services under one DB transaction. Persist the audit transition and essential notification record with the write; deliver any optional external alert after commit. Begin with on-demand reporting selectors and indexed queries. | Eventual-consistency between a charge and a checkout is unacceptable. Redis, Celery, distributed services and polling workers add failure modes. Revisit caching or a durable delivery queue only against measured load or approved delivery/retry guarantees. |
| ADR-007 · Proposed | One property, staff-facing operation, named spaces, hotel-local business date (candidate `Africa/Nairobi`), controlled access to histories and media. Keep student/participant identifiers and source artwork out of public Git. | Property tenancy, day use, guest portals or pooled parking would change keys, scope or workflows. Confirm with hotel and owner before Phase 4. Required private academic submission fields can be supplied separately. |

The principal records the decision owner, date, status, evidence and superseding ADR when a proposal is accepted, changed or rejected. See [Django PostgreSQL constraints](https://docs.djangoproject.com/en/5.2/ref/contrib/postgres/constraints/) and [DRF session authentication](https://www.django-rest-framework.org/api-guide/authentication/#sessionauthentication) for the mechanisms considered.

**Implementation update (2026-11-26):** Following the owner's build instruction, the principal selected ADR-002 through ADR-007 as engineering defaults for this single-property edition. The [build contract](../system-design/build_contract.md) defines the specific choices: room service posts on serving, departure requires full settlement and no open orders, and posting/receipt timestamps drive separate daily figures. The hotel has not validated these as real operating policies.
