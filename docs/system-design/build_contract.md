# Build contract: Hotel A staff edition

The owner directed the team to build after the discovery report. Treat these as documented software defaults; do not present them as field findings. One property; Africa/Nairobi; whole booking shares one date interval, primary guest and folio. Each booking can contain multiple named rooms. Integer BigAutoField IDs; fixed Decimal(12,2) KES; timestamp with timezone. Audit and state-changing events share the transaction.

## Shared implementation interface

Packages `apps.core`, `apps.lodging`, `apps.housekeeping`, `apps.restaurant`, `apps.billing`, `apps.parking`. Each exposes `urls.py` with urlpatterns included directly under `/api/v1/` (do not prefix twice). DRF page-number pagination `{count,next,previous,results}`, default 25, `page_size` max 100. Use `?search=` and useful status filters. No routine DELETE: preserve history. All domain ViewSets derive `apps.core.api.SecureViewSet` (GenericViewSet, override or mix in CRUD); declare `access = {'list':'rooms.view', ...}`; undefined actions denied; `apps.core.access.can(user, capability)` considers Django permissions. `apps.core.api.Conflict(detail)` HTTP 409; DRF ValidationError 400. `apps.core.events.record(user,verb,instance,summary)` writes a non-sensitive AuditEvent. `apps.core.images.SafeImageField` accepts only safe bounded re-encoded raster uploads via multipart, output authorized URL. No user-supplied financial totals or workflow status. Use django User, Groups canonical names Super Administrator, Hotel Manager, Receptionist, Housekeeping Staff, Restaurant Staff, Accountant, Maintenance Staff; group membership validated via core. Staff is User plus profile; staff id equals user id. `apps.core.access.is_manager(user)` for full task/order scope. Housekeepers/maintenance see only assigned records; restaurant handles department orders; finance sees no unnecessary guest data.

## Physical contract (field names are also ORM interface)

- core.StaffProfile(user OneToOne, department string, session_version, verified_email), AuditEvent(actor FK nullable,verb,entity,object_id,summary,created_at), Notification(recipient FK,title,message,created_at,read_at nullable); auth User, Group, Permission, Session. The database enforces uniqueness of nonblank, trimmed, lowercased recovery addresses. Notifications use scoped operational task feeds and persistent recipient items.
- lodging.Guest(full_name,email,phone,reference unique,created_at). Hotel-issued guest ref; normalized nonblank unique email if supplied; do not deduplicate by name. lodging.Room(number unique,category choice Single/Double/Twin/Deluxe/Suite/Family,nightly_rate,capacity,description,facilities JSON string list,image optional,cleanliness `inspected|dirty`,is_active). Numeric fields validated. lodging.Reservation(guest,arrival,departure,status `pending|confirmed|checked_in|checked_out|cancelled`,checked_in_at,checked_out_at,created_at); lodging.RoomClaim(room,reservation nullable,maintenance nullable FK housekeeping.MaintenanceRequest,start,end,blocking bool,nightly_rate decimal); one source, nonempty interval, same room nonoverlap on `[start,end)` where blocking, PostgreSQL btree_gist. Pending claims do not block; confirm locks rooms, commits all; create defaults to confirmed, optional `confirm:false` pending. lodging.ReservationEvent(reservation,actor,status,note,created_at). Occupied = room of checked_in reservation, independent of calendar/cleanliness. No overbooking/invalid admissions.
- housekeeping.CleaningTask(room,assignee nullable User,status `pending|assigned|in_progress|completed|inspected`,notes,created_at); housekeeping.MaintenanceRequest(room,assignee nullable User,description,start,end,status `open|resolved`,blocking,created_at). Open blocking work atomically claims inventory. Checkout calls `apps.housekeeping.services.turnover(room,user)` inside transaction; creates dirty pending task. Completed != inspected. Inspection cannot admit occupied/blocked room.
- restaurant.MenuItem(name,category string,price,available,image,description); restaurant.Order(reservation nullable,assignee nullable User,status `pending|confirmed|preparing|ready|served|cancelled`,created_at); restaurant.OrderItem(order,menu_item,quantity,unit_price). Room service points to an open booking, optionally designated `room` FK to one booked room; for multi-room require room selection. Checkout calls `apps.restaurant.services.assert_no_open_orders(reservation)`; same reservation → invoice → order lock order, creation and serving. Serve posts exactly once; dine-in creates standalone invoice. No gathering payments in restaurant.
- billing.Invoice(reservation nullable unique,created_at,closed_at nullable); billing.InvoiceItem(invoice,description,quantity int,unit_price,source_key unique); billing.Payment(invoice,amount,method `cash|bank|mobile_money|card`,reference unique,received_by User,created_at); receipt no. derived from immutable payment ID. `apps.billing.services.open_folio(reservation,user)` at check-in posts room claims' agreed rate × booked nights (early departure retains agreed charge; no implicit refund); `close_folio(reservation,user)` refuses unpaid balance; `post_order(order,user)` called at served under transaction. Allow real received cash/confirmed external tender only, require actual evidence/reference and stable idempotency; one receipt per tender, no overpayments. `total`, `paid`, `balance` decimal strings. No gateway.
- parking.ParkingSpace(code unique,is_active); parking.Vehicle(guest,plate normalized unique); parking.Allocation(space,vehicle,started_at,ended_at nullable). Partial unique active per space & vehicle. Never expose plates to other departments.

## API and capabilities

Lead review: InvoiceItem also has indexed `created_at` for local-day billing summaries. The reviewed dictionary/ERD are in `database_design.md` and `../diagrams/erd.mmd`.

URLs below end in `/`. JSON fields match model field names. FK values are numeric IDs. Include displays as convenient, don't replace ID. Mutations return resource. Same-origin session and Django CSRF; browser service prefixes `/api/v1/`.

|---|---|---|

| `auth/recovery-email`, `auth/recovery-email/confirm` | POST `{}` sends a verification link to the signed-in employee's registered address. POST `{token}` confirms it under the same account. An unverified address cannot receive password resets. | authenticated session + CSRF |

Omit unauthorized keys/feeds; money refers to lines/payments posted today, never doubles room service. | `dashboard.view`, scoped other grants; `audit.view` |

Grant manager all except `staff.manage` (super admin administers accounts); reception: dashboard, guests view/manage, rooms view, reservations view/manage, parking view/manage, billing view (folio lookups only, no posting). Accountant: dashboard + billing view/manage. Housekeeping Staff: dashboard + housekeeping view/work; Maintenance Staff: dashboard + maintenance view/work; Restaurant Staff: dashboard + restaurant view/work/manage (menu management). Managers dispatch and inspect. A non-superuser must belong to **one** canonical role and hold the Django permission: direct grants cannot raise that role's ceiling. Django superuser is the bootstrap exception. Reception uses `invoices/?reservation=<id>` or a particular stay folio; an unfiltered list contains no balances for this role. Broad list data requires appropriate grants even through drill-downs.

## Frontend integration

Shared module `src/services/api.ts` exports `api<T>(path:string, options?:RequestInit):Promise<T>`, `send<T>(path:string, method:'POST'|'PATCH', body?:unknown):Promise<T>` (FormData supported), `Page<T>`, `SessionUser`, `useSession()` from `src/services/session.tsx` returns `{user:SessionUser|null,refresh:()=>Promise<void>,loading:boolean}`; `can(user,capability)`. Start paths e.g. `rooms/`, no leading `/api/v1`. Page exports (all named, no props) `GuestsPage,RoomsPage,ReservationsPage` from `features/frontdesk`; `HousekeepingPage,RestaurantPage,ParkingPage` from `features/operations`; `BillingPage,StaffPage` from `features/office`. Shell owns dashboard, auth, router; routes `/`, `/guests`, `/rooms`, `/reservations`, `/housekeeping`, `/restaurant`, `/parking`, `/billing`, `/staff`, `/reset/:uid/:token`. Shared semantic CSS `.page`, `.page-header`, `.eyebrow`, `.panel`, `.toolbar`, `.btn`, `.btn.primary`, `.btn.secondary`, `.form-grid`, `.field`, `.table-wrap`, `.badge`, `.error`, `.notice`, `.empty`, `.card-grid`, `.actions`, `.muted`; use semantic accessible native controls. No fallback mock data. Prefer separate detail/form modules and real pagination over generic JSON editors.
