# Hotel A — physical database dictionary

**Design for lead review, not an applied schema.** The [build contract](build_contract.md) fixes the fields and workflows; the [physical ERD](../diagrams/erd.mmd) shows the tables and actual FK directions. One property, one primary guest and one date interval per reservation, one folio per admitted booking. These are software defaults, not findings about Hotel A.

## Reading the dictionary

- Names are PostgreSQL table/column names under Django's default naming. An ORM relation `room` is stored as `room_id`; an arrow points **from that column to its parent PK**. `?` means SQL NULL allowed; everything else is NOT NULL. `U` means unique. Every application table below has an implicit `id bigint` generated PK (`BigAutoField`), including junction-like business records. An FK uses its **target** width: `bigint` for domain parents, `integer` for stock Django `auth_user`. A profile's internal row ID is **not** a staff ID: every staff URL, assignee and actor uses `auth_user.id`.
- `vN` = `varchar(N)`; `money` = `numeric(12,2)` KES, never float or PostgreSQL's locale-dependent `money` type; `ts` = `timestamp with time zone`. Date columns are local calendar dates in `Africa/Nairobi`; store instants as aware timestamps. `created_at`/`started_at` are server-set at the event, not client inputs. Widths and blank-string conventions not fixed by the contract are physical design choices for review. Optional form text uses `''` rather than two missing-value representations. Images are private storage **keys**, not bytes or permanent public URLs.
- PKs, required FKs, unique keys, checks and exclusions below are DB rules. A referenced operational row is retained: use protected domain FKs, disable users/rooms/spaces or close/cancel instead of deleting. Nullable assignment means *unassigned*, not permission to erase staff history. `AuditEvent.actor` may be `SET_NULL`; Django owns its auth bridge lifecycles. No routine DELETE or client-writable audit/status/totals. Cross-row workflow rules below run in the same transaction as history/audit.

## Calendar and occupancy: two different questions

PostgreSQL enforces the following on **`lodging_roomclaim`**, not by inspecting a reservation or maintenance status in an index predicate. `daterange` is an expression over the two date columns, not a third column.

```sql
CHECK ((reservation_id IS NOT NULL) <> (maintenance_id IS NOT NULL)),
CHECK (isfinite("start") AND isfinite("end") AND "start" < "end"),
EXCLUDE USING gist
  (room_id WITH =, (daterange("start", "end", '[)')) WITH &&)
  WHERE (blocking)
```

**Sellable nights** = active room and no overlapping blocking claim for the requested nonempty interval. `[10,12)` and `[12,13)` can both commit; `[11,13)` conflicts with `[10,12)` even when one source is maintenance. A search is not a hold. **Occupied now** = a claim for this room whose reservation is `checked_in`, regardless of the night range, the blocking bit or cleanliness. An overdue occupant is still present. A future sale does not imply present occupancy. **Admissible now** additionally requires a confirmed booking for the local date, active room, vacancy, inspected cleanliness and no applicable blocking maintenance (ignore the booking's own claim when checking conflicts).

- Create with one or more distinct physical rooms for the whole interval. Snapshot each agreed rate on its claim. Default confirmation makes every claim blocking; explicit pending makes none blocking. Confirm/amend locks the reservation and the *sorted union* of old/new rooms, then rechecks activation, dates and conflicts. Update all claims/status/event together or none; cancel only an eligible pre-admission booking and clear its blocking flags. No post-admission edits to the room list. FK presence alone cannot enforce a booking has rooms or that dates match its claims.
- For an open blocking work request, lock the room, verify vacancy if blocking it now, create the request and its matching blocking claim (same room/window) together. An overlap aborts the whole operation; do not silently displace a booking. Resolve under the same room lock and release the unused block. A work request is the parent of a nullable **ordinary FK**; the workflow writes one calendar window for a blocking request, not an FK on the request pointing back at a claim.
- All admissions, departures and readiness changes serialize on the same physical room rows. Check-in locks/rechecks *every* booked room, then sets actual arrival, opens one folio and writes history atomically. This prevents two actual occupants even for adjacent **non-overlapping** reservations: the GiST rule alone cannot do that. On checkout verify `checked_in`, no open orders and zero balance; set actual departure, close folio, release unused nights and call turnover for each room (dirty + pending task), all in one commit. A rejected/repeated checkout cannot create a second task.
- On early checkout keep the sold historical prefix `[start, local_checkout_date)` blocking if nonempty and release only the unused tail. If no night elapsed, keep the original valid dates but clear `blocking`; never write an empty range. At/on or after the planned end, leave the original nights intact. **Do not shorten the reservation's contracted dates, recalculate room charges or extend a sale silently** because of actual departure. Assignment/inspection locks the affected user/room as needed and rechecks active role/current task. Only authorized inspection, not mere completion, can release cleanliness; an occupied or currently maintenance-blocked room cannot be admitted by inspection.

## Atomic commands and finance

At PostgreSQL READ COMMITTED use an explicit transaction and row locks, then re-read state **after** obtaining them. Shared order for existing rows: **reservation → invoice → order(s) → room(s)**, skipping unused classes, PK ascending within each class. Children are changed under their locked owner. A new invoice/row is private to its creating transaction. Never take a room/task lock and then request a parent reservation lock, or start with an order/payment lock and work back to its invoice. Task/work-only services lock room before task/work; revalidate selected staff and menu items under locks before assignment/order commit. Do not rely on locking an empty query result.

| Command | What the lock and transaction protect |
|---|---|
| Check-in / `open_folio` | The reservation is the creation lock for its as-yet absent unique folio. One line per booked room, e.g. `room:<claim-id>`, quantity = `departure - arrival` in local **nights**, price = that claim's agreed rate. Room checks, state, events, lines and their posting audit either all commit or all roll back. |
| Room order create / transition / serve | Lock its reservation, then its folio, then the existing order if any. Revalidate status, immutable booking/room binding and open folio; lock menu items by ID and recheck availability when selling. Creation does not bill. At serve, change order state and post each order item once under a stable key such as `order:<order-id>:line:<item-id>`, copying accepted quantity/price, not current menu price. A committed replay reads existing lines; it is not a new posting. |
| Dine-in serve | NULL reservation/room; one standalone invoice for the served order's lines, no guest/payment fabricated. The source keys identify its invoice without an uncontracted FK. For first serve, insert a candidate standalone invoice **in the serving transaction before locking the order**. Re-read the order under lock: if a concurrent serve won, roll back the candidate before returning the committed posting by source key; on any refusal roll it back too. Never leave a spare invoice or lock a winner's invoice while holding the order. |
| Additional charge / payment | Read immutable invoice ownership to identify the reservation; lock that reservation if present, then invoice. Check stable source/tender key first: an authorized identical retry (even after close) returns the original result; mismatched invoice/amount/method or charge payload is a conflict, not disclosure of another invoice. For a new entry, require open invoice. Extras use a distinct stable namespace, e.g. `extra:<invoice-id>:<reference>`. Recompute balance under lock; require verified tender or physically received cash, authorized receiver, `0 < amount <= balance`, valid method and real reference. Reject non-finite/excess-scale inputs **before** DB decimal coercion. Global unique reference also arbitrates races across invoices: on uniqueness failure roll back the failed write/savepoint before re-reading. No second receipt. |
| Checkout / `close_folio` | Lock reservation, folio, then any relevant orders, before room turnover. Order creation uses that **same reservation lock**, so an empty open-order scan cannot acquire a phantom order before commit. Any status other than `served/cancelled` blocks checkout. Recompute unpaid amount under invoice lock, refuse nonzero. If serve wins, checkout sees the line; if closure wins, no later room charge/order/payment is created. Never mark unpaid funds received to close. |
| Parking | Lock space → vehicle → existing allocation when applicable, stable PK order; recheck active space and both active-allocation keys. Partial indexes are the final arbiter even on concurrent first inserts. A release stamps `ended_at` once. |

`total = Σ(quantity × unit_price)` over invoice lines; `paid = Σ(amount)` over its payments; `balance = total − paid`, empty sums `0.00`. Aggregate each child set **separately** before combining; joining raw lines to raw payments multiplies both. Return decimal strings. For example, two booked nights at KES 2,000.00 plus KES 850.25 served, less KES 2,000.00 actually received, leaves **KES 2,850.25**. Orders are not additional revenue on top of their invoice lines.

**Posting date:** `billing_invoiceitem.created_at` is a required indexed timestamp with time zone set when the charge is posted. Daily `billed` sums invoice items by this timestamp; `collected` sums payments by their own timestamps. Neither invoice creation time nor order creation time is a line's posting time. Audit is independent; apply the same authorization scopes to summaries as to detail.

## Access paths and normalization

- PK/unique keys already have B-trees. Django FKs are normally indexed; PostgreSQL does **not** automatically index referencing columns. Avoid redundant copies. Use the partial GiST for blocking overlap; retain room/booking FK access for occupancy even on nonblocking rows. Useful B-trees: Reservation `(guest_id, created_at)`, `(status, arrival)`, `(status, departure)`; ReservationEvent `(reservation_id, created_at, id)`; MaintenanceRequest `(room_id, status)`. Exact guest reference/canonical email and room number have unique lookup paths. A plain B-tree is not a substring-name-search index.
- Task `(assignee_id, status, created_at)` and `(room_id, status)`; Order `(reservation_id, status)` for checkout and `(status, created_at)` for the department queue. OrderItem/InvoiceItem owner FKs, unique source/tender keys and Payment `(invoice_id, created_at)` support detail/reconciliation; individual posting and payment timestamps support daily figures. Audit `(entity, object_id, created_at)`; unread Notification `(recipient_id, created_at) WHERE read_at IS NULL`. Space/vehicle active keys are also availability indexes. Confirm additional non-unique indexes with `EXPLAIN` on representative data before release.
- Guest, staff, menu, room and parking facts live once. RoomClaim resolves booking ↔ named rooms and shares the exclusion surface with work; OrderItem resolves order ↔ menu, Allocation preserves successive space/vehicle associations, auth bridges resolve membership/grants. Header and line attributes depend on their own keys, not on copied guest/assignee details. A price agreed/sold/posted is a fact **at that event**, not a cache of today's tariff. Balances, receipt labels, occupancy, room availability and dashboard counters are derived.
- The logical design targets 3NF, with explicit physical exceptions: claim interval/room/blocking are local enforcement projections synchronized by the source transaction; current workflow state and append-only event history serve different queries. Facilities is a bounded descriptive JSON list, not a normalized facility catalog; do not hide room IDs, quantities, permissions or money in JSON. No separate Stay, Receipt, OrderInvoice link or guest list is assumed by this contract.

## Migration and acceptance gate (plan, not execution)

1. On every target **database**, including isolated test DBs, preflight availability and permission to install `btree_gist` (or have the DBA provision it). Use Django's `BtreeGistExtension` before creating the exclusion. Range overlap is native; the extension supplies GiST equality for the scalar `bigint` room key. Fail the release if unavailable; never silently omit the constraint or substitute SQLite.
2. Integrated migration order: `housekeeping.0001` establishes the task and work tables. `lodging.0001` depends on this base, enables `btree_gist`, and creates the lodging tables, including the complete RoomClaim and its exclusion. `housekeeping.0002` then adds the room references and remaining constraints. Django resolves the cycle by deferring those references rather than deferring the entire claim table. Core uses auth; restaurant/billing/parking depend on their actual FK parents. Service calls are not migration dependencies; enable workflows only after all migrations apply.
3. Lead verifies from an empty PostgreSQL DB and a restored disposable copy: inspect FK targets, nullability, money scale, partial unique/exclusion definitions, extension and dependency order; rehearse rollback in reverse dependency order without dropping a shared extension in use. Then use two independent transactions and inspect committed state from a fresh connection: adjacency vs overlap, same-room maintenance vs multi-room confirmation (no partial claims), disjoint-night admission vs overstay, serve/create/payment vs checkout, duplicate tender/excess payment, early checkout/turnover, and same-space **or** same-vehicle races. Exercise both winners and forced rollback; include same-day release, retained price/posted-day reconciliation and unauthorized histories. Diagram/dictionary review precedes models; none of these runtime tests is claimed here.
