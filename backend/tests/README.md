# B10 · staff API acceptance gate

This directory specifies expected outcomes. **The existence of a test is not a pass.** Record the commit, PostgreSQL version, migration state, command, counts and failures from the actual run separately. These tests create synthetic guests, staff, tenders, rooms and plates in a disposable Django test database. They never contact a hotel or payment provider. Reset mail stays in memory; the authorized-download test writes only to pytest's temporary media directory.

From `backend/`, with `requirements-dev.txt`, the project's test environment and a **dedicated PostgreSQL instance** configured:

```text
python -m pytest tests/test_contention.py -q -ra
python -m pytest tests -q -ra
```

Allow the runner to create/drop a test database and apply the real migrations, including `btree_gist`. Do not use production credentials, `--no-migrations` or SQLite. Role fixtures use the canonical groups installed by `post_migrate`; they never create grants themselves. A Django superuser bootstraps independent domain fixtures. The full journey uses ordinary staff accounts. Browser-auth tests require actual session cookies and CSRF checks; business-command tests use DRF's in-process client. This is not browser, component, HTTPS-deployment or recovery evidence.

## Why the contention result is meaningful

[The harness](overlap.py) uses `django_db(transaction=True)`, a thread-local API client and a real PostgreSQL session per contender. A bounded two-party barrier runs **inside both HTTP requests**. The test holds the first request's transaction at its commit boundary until `pg_blocking_pids` observes the second backend waiting for the first. No test lock is taken on the inventory, invoice or other domain row. A timeout or absence of actual blocking fails the test. Worker connections are closed and committed state is inspected from a fresh, third backend. The deliberate rollback case distinguishes a tentative success inside the transaction from durable success.
